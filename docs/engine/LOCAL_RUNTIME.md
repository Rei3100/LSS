# Engine | Windows Local Runtime and Reliability

Normal audio inference is local and GPU/CPU/disk-aware. Source media never goes to a hosted or external separation, analysis or judging service, and paid per-request services are excluded. Public metadata/released media can be optional; offline absence must gracefully preserve useful locally processed outcomes.

## Operational identities
Source code/commit, capability/Recipe, test Evidence, built package, deployed EXE, mutable Product state and current user library are different identities. A builder's executable and a green suite do not establish live deployment.

## Publish and recover
Stage new outputs and verify before public pointer change. On failure, existing valid CurrentBest, provenance, tags and artwork remain. Recovery must handle retry, partial writing, locking, crash, restart, missing output and the rerun of a Source already present. Reusable artifacts should prevent needless inference. An output filename alone never proves completion: durable job state records what was planned, completed, staged, verified and published, and database and filesystem publication are not one transaction, so startup reconciles them.

A recovery claim needs failure-injection tests: provider crash, application crash, forced termination, interrupted download, out of disk, corrupt candidate, restart between publication steps, provider OOM or runtime initialization failure, and compatibility failure right after a model/runtime update. Provider and helper process trees are cleaned after cancel or crash (Windows process-tree control). Database backups are verified and kept in several generations, and schema migrations are explicit and versioned.

## Artifact trust and secrets
An unverified executable, runtime or model is never activated automatically. An update runs discover, acquire, verify, stage, validate, promote; a candidate that fails verification or compatibility/quality validation stays HELD, and a model or provider update also shows no regression in the adopted role, target-absent behavior, rate/channel/timeline and known failure signatures. Trust is recorded per axis, never as one boolean: expected source, revision, hash, signature or attestation where available, code licence, weight/data licence, scanner result, local compatibility, runtime behavior. Scanner results, signed provenance and a hub's security scan are evidence, not proof of safe behavior or of exact artifact identity. FFmpeg upstream ships source only, so both the upstream identity and the actual Windows build/provider/hash are recorded; the public yt-dlp checksum or signature is used and recorded when available, and an updater candidate that cannot be verified is not activated.

Cookies, tokens, passwords and other credentials never appear in Markdown, logs, provenance exports or model-visible diagnostics; only the kind of authentication or the credential source is recorded, apart from the secret, and persistence is minimal.

## Deployment
Promotion is an exact artifact and state transition. Verify source/EXE identity, intended supported scope, real packaged acceptance and rollback for changed surfaces. Retain known-good rollback snapshot and check mutable user state during rollback. Do not require every isolated experiment to perform a full deployment ritual.

## GUI without taking over the desktop
Recover historical offscreen/unattended app harnesses, CLI/UI handlers and package tests before inventing new restrictions. A pixel-level visible GUI observation can require a desktop session; never conflate this with inability to run noninteractive Product-path validation. The user should continue using Windows normally.

## Release runbook (actual scripts)
1. **Build an exact commit on SSD:** `scripts/build_candidate_offdrive.ps1 -Commit <sha> -Worktree %LSS_C_WORK_ROOT%\wt\build-<sha7>` (new detached worktree, SSD `.venv` junction, `build.ps1`, runtime-source check). Prints the EXE SHA-256 using the shared Python runtime, without requiring PowerShell module discovery. Keep the source worktree on C; policy-owned build/dist and child temporary paths resolve to D (docs/dev/DATA_LIFECYCLE.md).
   To run it in the background without a window, give `scripts/hidden_run.py` a reservation that covers the build's own: `--log <log> --storage-gb 12 --protect <worktree> --protect <build_data> --protect <worktree>.build-receipt.json`, with `build_data` taken from `-Plan`, then `-- pwsh -NoProfile -ExecutionPolicy Bypass -File scripts/build_candidate_offdrive.ps1 -Commit <sha> -Worktree <worktree>`. The build's nested reservations reuse that one only within its estimate and paths, so a smaller estimate, or one of these paths left outside every protected path (hidden_run itself adds only its working directory and the log's folder), is refused with "nested expansion refused".
   `-Plan` resolves the exact commit, current/shared Git root, shared Python and policy-owned output location before preparation. Normal execution reserves both lexical and resolved build paths before copying vendor files or creating the worktree, preserves shared Git settings, and records preparation/build/source-check failure in the adjacent `.build-receipt.json`. Existing worktrees/receipts are retained for diagnosis; a failed preparation does not authorize cleanup or automatic replay.
2. **Freeze**: write a per-file SHA-256 package manifest next to a short handoff (identity, delta from the previous candidate, test entry points), set the package read-only. Nothing in the frozen package changes afterwards; a fix is a new candidate. The freeze refuses a candidate lacking Product commits of any branch active in the last 21 days unless each such branch is excluded with a reason (`--exclude-file`); a candidate is the latest integrated Product, not one line.
3. **Builder packaged checks**: the harness copies the package and runs on clones of real r4 states (`%LSS_DEV_COLD_ROOT%\claude-integrated\accept\tools-r*`: A = BGM CurrentBest/listening/restore round trip on four episodes, B = Instrumental reuse, C/C2 = references and upgrade on real r4 state, D = reference vs no-reference wanted-music preservation). GPU steps take `%LSS_DEV_COLD_ROOT%\claude-integrated\gpu.lock`. The r4 baselines predate the installed release: A and B fail identically on installed 6c93897 (stale baseline, not a regression; `release-evidence/strata-deploy-20261031/c76b88f4/packaged/DISCRIMINATOR-6c93897.md`). A candidate's A/B failure is therefore compared once against the installed release's package, never re-run on intermediate parents whose diff does not touch the failing path; regenerating the baselines from the installed release removes that comparison.
4. **Independent verification** by a different agent on the frozen bytes; verdict PASS / FAIL / HOLD.
5. **Deploy** only an accepted candidate. Write the private state JSON at `$LSS_PRIVATE_ROOT/run/deploy-gate.json` by default, using the absolute paths and keys in the [Deployment evidence contract](../../gates/ENTRY_POINTS.md#deployment-evidence-contract). The state's `deploy_base` and `current_product` describe the same installation. The record at `current_product` names `<deploy_base>\LSS\LSS.exe` as `deployed_executable`, and the rollback receipt describes that executable and its SHA-256.

   Set `deploy_log` and `launch_receipt` to distinct paths outside the checkout named by `repo`, the frozen package, and `deploy_base`. Use a private directory such as `$LSS_PRIVATE_ROOT/run`. Create an empty file at `deploy_log` before either gate call. Use an unused path for `launch_receipt` so the launcher can create the receipt.

   Capture the file list and SHA-256 hashes of the user's Product state (P) before taking the idle observation. If a saved queue exists, keep a private copy for the final comparison. Record the observation in `idle_receipt`, then run the installed `deploy-gated.cmd --check-only` and require every condition to pass. On PASS, run the installed `deploy-gated.cmd`. At each gate call, `observed_at` must be between 0 and 60 seconds old, inclusive. Refresh the observation if it expires before the second call. Use `--state <json>` on both calls to select a different state file.

   The gate rechecks the conditions and requires the checkout named by `repo` to be clean, with `HEAD` and `origin/main` at the candidate commit. It launches `deploy-to-freesoft.ps1 -BuildOutput <frozen package> -DeployBase <base> -KeepPrevious` through `hidden_run.py`. `LAUNCHED` reports process launch. Use the launch receipt to track the process, wait for it to finish, then confirm success in the deployment log and `awaiting_acceptance` in `<base>\.LSS-deploy.json`.

   The script stages and verifies the payload, stops processes whose executable path exactly matches the installed target, and swaps in the runtime under `<base>\LSS`. It retains `.LSS.previous` and the journal and preserves mutable and unknown user entries. Before starting acceptance, verify the relative paths, sizes and SHA-256 hashes under `<base>\LSS` for the package files listed in the frozen manifest. Keep mutable data such as `.state` and `models`, unknown user files, and the installer's own `.lss-runtime-manifest.json` out of the payload comparison.

   From the checkout root, run `.\.venv\Scripts\python.exe scripts/post_deploy_bgm_check.py --source "<episode.mkv>" --install "<base>\LSS"` for a representative BGM job on a scratch copy that mirrors the installed link layout. Require a fresh PASS receipt from this run with the frozen candidate's EXE SHA-256. Verify startup and processing on a hidden desktop with the newly installed executable. Use the following PowerShell commands, substituting the state file's `deploy_base` for `<base>`. Leave `LSS_UI_ACCEPTANCE_DOWNLOAD` unset.

   ```powershell
   $env:LSS_RUN_UI_ACCEPTANCE = '1'
   $env:LSS_ACCEPTANCE_EXECUTABLE = '<base>\LSS\LSS.exe'
   .\.venv\Scripts\python.exe scripts/dev.py test --suite ui-acceptance tests/test_ui_deployed_acceptance.py
   ```

   The UI harness starts the copied EXE with the deployed bundled resources and temporary state. Accept `PASSED`, or `PASSED_WITH_SKIPS` when the first-run download test is the only skip. An all-skipped run fails acceptance. Frozen worker startup can create an automatic backup under the actual app root even with isolated state.

   Rehearse step 6 once while acceptance is pending. After rollback succeeds, set `deploy_log` to a new empty file and `launch_receipt` to an unused path as above. Record a fresh idle observation in `idle_receipt` before repeating the gate calls. After redeployment completes, verify the payload again. Rerun the BGM check so it overwrites `<base>\.LSS-postdeploy-bgm.json` with the result of the redeployed run, then repeat UI acceptance.

   Before finalizing, start the installed `<base>\LSS\LSS.exe` once on a hidden desktop using the user's real Product state. Confirm that it reaches idle (`ready`) without starting a job. The scratch checks use separate state directories, so they cannot show startup failures caused by the real `.state`.

   End every harness-owned installed process after the real-state startup, then compare P's file list and hashes with the pre-deploy snapshot. The user's results must be unchanged: every existing CurrentBest record, release record, generated audio file and music-library file keeps its path and hash, and none is removed. Other differences under `.state` and `<base>\LSS\Backups` are the Product's own startup writes, for example the saved queue dropping completed or skipped entries (verify against the saved queue copy), an automatic backup, appended log lines and the page rebuilt under `.state\web`. List them in the acceptance record.

   Run `deploy-to-freesoft.ps1 -Finalize -DeployBase <base>` only after the rollback rehearsal succeeds, the redeployment passes all acceptance checks, and the retained package is no longer needed for immediate recovery. The script requires `.LSS-postdeploy-bgm.json` under the deploy base with `PASS` and the installed EXE's SHA-256.

   After finalization, record the new release and its rollback command in the record named by the state's `current_product`. For the next deployment's `rollback_ready` check, use the successful installed startup to write a fresh receipt at `rollback_receipt` with the installed EXE's path as `exe`, its SHA-256 as `exe_sha256`, `status: PASS` and `startup_pass: true`.
6. **Rollback** while acceptance is pending. Before rollback, confirm that `<base>\.LSS-deploy.json` exists with phase `awaiting_acceptance` and that the directory `<base>\.LSS.previous` exists. End every harness-owned installed process, then run `deploy-to-freesoft.ps1 -Rollback -DeployBase <base>` to restore the retained runtime. If the previous release has a frozen manifest, apply the same payload comparison as in step 5 under `<base>\LSS`, using that manifest. For a release that predates frozen manifests, use its recorded restore command if you need to reinstall it from its package. In either case, verify the restored EXE against the SHA-256 in `current_product` and confirm that it starts successfully. Compare P with the pre-deploy snapshot using the same allowed differences as in step 5, and verify that the music libraries are preserved.

   `-Finalize` removes `.LSS.previous` and the deployment journal. If the installed EXE is missing or its SHA-256 differs from the release record, `rollback_ready` blocks every deployment through the gate. Use the rollback command recorded with the release in the record named by the state's `current_product`. A release can record a script such as `.state\releases\<release>\restore-*.ps1`.

   Run the recorded restore command with the state's `deploy_base`. Set `$env:LSS_DEPLOY_BASE` to that path in the PowerShell session that runs the restore command, or pass it as `-DeployBase` on each installer call. Before relying on the command, verify that each installer call uses that path, including any explicit `-DeployBase` that overrides the environment variable.

   The restore command deploys the recorded package with `-KeepPrevious`. If the command also calls `-Finalize`, set aside any existing `<base>\.LSS-postdeploy-bgm.json` before running it so an earlier receipt cannot finalize the restored package. A refusal at `-Finalize` due to missing or mismatched BGM evidence leaves recovery pending. Once the restored payload is in place, rerun the BGM check from step 5 against `<base>\LSS`. It overwrites `<base>\.LSS-postdeploy-bgm.json` with the restored EXE's result. Require `PASS` and the restored EXE's SHA-256, confirm the installed EXE reaches idle on a hidden desktop with the real Product state, and end the harness-owned processes before running `deploy-to-freesoft.ps1 -Finalize -DeployBase <base>` to finish recovery. Before running the gate again, make sure `current_product` and `rollback_receipt` describe the restored installation.

   A gated return to an older release after finalization is a new deployment from a revert on `main`. `deploy-gated.cmd` refuses the older commit while `origin/main` points to the new release. Build, freeze, verify and deploy the resulting `origin/main` commit through the same gate.

## Bounded resources
No silent quality-changing fallback: contention, OOM or memory pressure never switches silently to CPU, a smaller model, a shorter context or lower precision. Only a fallback the Recipe allows runs, with the branch and RuntimeRevision recorded; a worker recycle that leaves quality unchanged is allowed, and GPU-heavy jobs are serialised where that protects quality. Provider I/O that affects output (native and output rate, channel handling, implicit resampling/downmix, effective bandwidth, segment/context/padding, algorithmic delay, precision) is recorded or measurable: a 48 kHz output file proves neither 48 kHz inference nor retained bandwidth.

Respect actual GPU/VRAM, disk ownership, active tasks and network pacing. Keep ephemeral inference work on designated cache/scratch storage when possible. Code/test package work may run in isolated worktrees; serialize only true GPU or deployment collisions.

## Local language and speech models
A Product capability that uses a local LLM or ASR exists only when the frozen package runs it on the user's path; working from source is a Development result. The installed Product has the native whisper.cpp/llama.cpp naming backend (`lss/bgm/scene_runtime.py`, `lss/bgm/scene_native.py`); `lss/bgm/scene_job.py` can bootstrap it in the packaged app. The Transformers/bitsandbytes route remains source-only. Native ASR words are withheld from naming as `ASR_UNVERIFIED`, so the installed titles use context/music and scene-grounded titles remain unavailable. Runtime availability, successful naming and verified scene grounding are separate claims; exact installed identity and limits live in `.state/releases/current-product.json`.
- **On demand, never resident.** A model loads for one job, inside the cross-process GPU lease, and its process ends with the job; no LSS model server keeps running between jobs. A lease that cannot be taken stops the job (fail closed), and the lease and VRAM are released on every exit path. An external inference binary (e.g. llama.cpp `llama-server.exe`) runs as a hidden child of the leased job and is killed at its end: measured 2026-10-26, VRAM returned to baseline 0.8-3.2 s after the kill (one run 31 s). `llama-server`'s own idle sleep keeps ~600 MiB per model and is not a release.
- **Model choice is measured on the job, not on tokens/s.** RTX 5060 Ti 16 GB, llama.cpp b11878 CUDA 13.4, ctx 16k, f16 KV (2026-10-26, `%LSS_C_WORK_ROOT%\local-llm\RESULTS.md`): 9B Q4 fully on GPU pp 3,260 / tg 65 t/s, 5.5 GB RAM; gpt-oss-20b with 6 expert layers on CPU pp 1,650 / tg 47, 12.8 GB RAM; Qwen3.6-35B-A3B Q4 with 24 expert layers on CPU pp 520 / tg 44-49, 20-21 GB RAM, which drove system free RAM to 63 MB. A model whose CPU-offloaded working set leaves the PC without memory headroom does not run beside separation, tests or the GUI; the GPU lease does not cover RAM. A q8_0 K cache corrupts identifiers with Qwen3.6 (reported upstream): keep K at f16.
- **Weights are not cache.** Pinned-revision weights live outside the evicting model cache (`lss/core/models_store.py` cap and floor would count ~29.5 GB of scene-naming weights and evict separation models), and on the SSD when a job loads them repeatedly: cold loads from the USB HDD took 167 s (13.8 GB) and 177 s plus ~150 s of expert paging (22.9 GB), every start, because the file does not stay in the page cache.
- **Language output is never audio evidence.** A local model's text names, summarises or proposes; recording identity, wanted retention, residue and quality are decided by acoustic measurement (`docs/engine/QUALITY_AND_DECISIONS.md`). A model never supplies an identifier (test id, cue id, path, hash) that a deterministic reader can extract: on truncated input gpt-oss-20b invented a test id that was not in the log.

Development runner placement is enforced by resolved Windows volume identity: checkout, Python, temp, runtime and active model weights stay on SSD, and HDD-backed paths are refused. The three measured active GGUFs (Ornith 9B, gpt-oss-20b and Qwen3 embedding 0.6B) are permanently retained under `%LSS_WORK_ROOT%\local-ai-models`, separate from both Product models and the evictable stage. Cold originals remain archives. Post-correction 15 disk-counter samples during real model work reported zero E: read/write bytes per second and at most 1% activity; this is whole-machine observation over that window, not a guarantee about other agents. Exact results: `release-evidence/local-ai-practical-20261026/RESULTS.md`. These Development measurements do not establish the deployed native naming route's scene-grounding quality.

The experimental standalone Omni Thinker route derives its generation BOS/EOS/PAD from the component config; the outer Omni generation file omits those defaults and cannot supply its stopping contract unchanged. On three controlled stereo inputs, explicit EOS retains identical English answer objects and eliminates generated follow-on conversations (288 to 70 tokens); BF16, prompt and inputs remain equal. The 4.70B-parameter Thinker takes 9.41 decimal GB of parameter storage, despite the checkpoint's 3B text-model name. The route is Development-only, at duty 0.25 with model-size and transient-load headroom, and is not adopted for natural-music facts or naming. Exact limits and measurements: `release-evidence/local-ai-audio-r1/INFERENCE.md`.
