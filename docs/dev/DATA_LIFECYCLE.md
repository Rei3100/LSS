# Development | Storage Ownership and Cleanup

## Classes with different authority
1. **Durable Source/Asset/History:** user data and established Product truth. Preserve; provenance/lineage may outlive physical retired revision files.
2. **Durable machine Evidence:** frozen identity, case manifests, exact hashes, controlled outputs necessary for reproduction or acceptance.
3. **Compact Product intelligence:** references, features, relations and re-acquisition information; persist cheaply.
4. **Reusable cache/heavy reference media:** retain if time/reliability justifies; retire only under specific ownership and rebuild rules.
5. **Job scratch:** abandoned regenerable work can be reclaimed after proving it is not active/resumable.
6. **Unknown or user-owned files:** never infer deletion permission from folder name or disk pressure.

## Lifecycle transitions
Before retiring large artifacts, establish owner, active locks, dependencies, source identity, reproducibility, content hashes, restart expectations and rollback availability. Failed cleanup must be resumable. Compact record sufficiency does not imply every waveform can be discarded: donor reconstruction and independent Evidence may require original media.

## Development Evidence versus Product media
`.state/validation/` should point to small durable result manifests; bulky regenerable experiment data belongs in a separately owned local cache where appropriate, not accidentally in a user music folder. A frozen counterexample needed to explain an accepted/rejected Product decision remains durable even if the experiment is no longer active.

## C/D/E placement

The development machine has three volumes: C, the system SSD; D, a second fast SSD holding the work root (`LSS_WORK_ROOT`); E, a large HDD holding the media root (`LSS_MEDIA_ROOT`) and the cold development root. The machine's storage policy file owns the real paths and thresholds.

- **C — system and development foundations:** Windows, installed LSS executable, source checkout, Git/worktrees, shared Python environment and provider code/runtime dependencies. Worktrees remain under the C work folder (`wt`); their bulky build/dist endpoints can resolve to D.
- **D — hot data:** the D work root owns local-AI weights/runtimes, model stores, temporary/build data, staged HDD references, derived development caches and Product processing/cache payloads. Development and Product model stores remain separate under `models/development` and `models/product`; provider environments remain on C. The model stage is capped at 120 GB; permanent weights are excluded from LRU eviction. Child development jobs use D for TEMP/TMP without changing Windows-wide settings.
- **E — long-term storage:** original media, published assets, reference originals, completed research Evidence, cold outputs and backups. User source files stay unmodified. Inactive/oversized archive-only LLMs stay cold until selected; active LLMs execute from a verified SSD copy.

`scripts/storage_layout.py` runs inside the existing `LSS Storage Tiers` OS task. Explicit owned C paths are copied to D, every file is SHA256-verified, and the original path becomes a junction only after verification. Nested junctions (including missing archive links) retain their reparse records; HDD targets are neither copied recursively nor deleted. Existing unrelated D destinations are never overwritten. An interrupted switch is journaled and recoverable; changing or active sources remain untouched/deferred. The layout covers owned C work-folder data directories except `wt` and `accept-*`, model/cache directories and Product work/candidate payloads. Acceptance scratch belongs to age-based cleanup on each SSD, so independently existing C/D scratch is not migrated onto the other copy. It never scans or cleans unrelated data on D.

C and D are independently managed fast volumes. Development placement checks accept their resolved Windows volume identities and reject E-backed execution. Capacity reservations charge the actual SSD(s) behind protected paths, including C-to-D junctions; unknown legacy reservations charge conservatively. Stage pressure follows the resolved D cache volume. C free space cannot authorize a full D cache, and C pressure cannot evict a roomy D cache. The policy retains separate C/D admission floors and demotion watermarks. Automatic cleanup keeps `move_to_hdd=false`: verified unneeded items are deleted rather than moved to the HDD for retention. UNKNOWN, active, needed-later and unrecoverable items stay.

New builds keep source/worktrees on C and create build/dist endpoints under policy-owned D paths (`scripts/storage_paths.py`, `build.ps1`). Existing populated output is relocated only by the scheduled mover. HDD media for tests/probes/model loads uses `scripts/stage.py` (Python `stage_path()` in scripts/tests, never in `lss/`); the original remains E and repeated access uses the verified D copy. Development memory keeps its workspace binding while its derived cache resolves to D. Existing C references remain compatibility aliases, so migration does not rewrite cue identity, source records or rollback history.

The task wakes at logon and every hour, serialized, without an agent. `scheduled_cadence` admits SSD cleanup on every hourly tick and HDD-capable maintenance every 24 hours (a 10-minute slack keeps tick jitter from skipping a due pass). SSD pressure admits cleanup before its deadline; pressure relieved by that cleanup does not admit HDD work. A pending recovery journal admits HDD work. Successful groups alone advance their own SSD-local timestamp; unavailable process inventory and failed dependency scans remain failures and are retried. Healthy, not-due ticks check SSD capacity and local receipts without discovering cleanup targets. Session hygiene observes only. Journals/logs/last-pass receipts remain under `%LOCALAPPDATA%\LSS-dev\storage-tiers`; cold receipts remain under the cold development root (`cold\receipts`). `last-layout.json` records moves, active deferrals and failures. D placement does not replace E archival or backup: a second SSD is a working tier.

Known PC leftovers use owning-tool cleanup and explicit age rules. Failures are receipted without advancing success stamps. Quiet-policy deferral remains available. `scripts/local_ai_storage.py pin` creates same-volume hardlinks from a verified stage to the permanent D store; cache eviction does not remove permanent weights. The local-AI runner refuses HDD runtime/model paths. No Product EXE deployment is implied by physical placement.

Local model folders under `unused_local_models.roots` are deleted only with positive re-acquisition evidence in an in-folder `lss-model.json`. The record contains `source` (a public repository ID or HTTP(S) URL), an immutable exact `revision` (a full 40- or 64-character hexadecimal commit/content identity, never a branch or tag), `status`, `total_bytes`, and `files`: a mapping of every relative POSIX file path to its `bytes` and `sha256`. Only the root provenance record itself is excluded from the inventory. Cleanup verifies the complete inventory, total size and every payload SHA256 before deletion; missing, malformed or mismatched evidence is UNKNOWN. Status is explicitly `retired` (a recorded decision that the model is not needed again); `trial` and every other status stay, because a trial still in use or awaiting a decision is not evidence of being unneeded. Absence from saved launch profiles alone never establishes that a model is unneeded.

Every deletion also requires no saved Strata profile/preset reference, no name reference in the main checkout's tracked scripts/configs, no running command-line/current-directory consumer, no active storage reservation, no keep-list entry, and an idle age beyond both the general and model-specific policy thresholds. Reference discovery reads bounded text files and excludes secrets/auth files. A failed reference scan or incomplete process inventory keeps the model. Links and unreadable content stay. Cleanup refreshes these guards under the storage mutation lock and saves the re-acquisition record to a local receipt before removing the folder. Receipts and status report unclassified folders as `kept: unknown provenance`. Dry-run reports deletion candidates and keeps without removing files. Nested `.cache` directories have no implicit regenerability contract: their content requires the same complete provenance, and protected folders retain their caches. Other hot-cleanup rules do not bypass these protections in the configured model roots. No HDD archive is created.

## No forced housekeeping
Agent acceptance scratch (package copies, cloned states, mirrored junctions) lives under `accept-*` in the C or D work root, or `post-deploy` in the D work root; the `LSS Storage Tiers` task reclaims these regenerable copies after 24 idle hours (`temp_orphans` in `scripts/storage_policy.json`), retaining active command-line/current-directory users and storage reservations and removing junctions as links. Agents never delete it by hand and never report it as a leftover for the user; scratch outside these roots is a defect of the script that made it. Normal LSS decides routine owned-scratch reclamation without user intervention; Development agents must never clean unknown storage, inactive-looking worktrees or user-created media based on cosmetic diff or directory size alone. In `%TEMP%` only items with an owned prefix (e.g. PyInstaller `_MEI`) are reclaimed by age; other items there are of unknown origin and stay.

Named DLL/checkpoint inventory is read-only, bounded and refreshed weekly by the same OS task (`scripts/storage_inventory.py`, `dependency_inventory` policy). File IDs distinguish existing hardlinks from physical copies; SHA256 distinguishes versions. Stable prior hash observations let later passes verify files deferred by the I/O budget. Equal names/sizes never authorize model-copy deletion: canonical bytes must match. Managed DLLs across installed Product and Python environments remain separate, because independent updates do not provide an immutable shared-file contract. Contemporary installed `.state/bgm-candidates` runs remain durable Product state (reuse, held material, publication recovery and rollback). Pre-run.json activity-era payloads idle for 14 days are cold-archived with verified junctions under the Product owner lock; their metadata and all bytes survive. Unknown layouts stay. WSL distributions and VHDX files are user data; a missing registered path does not authorize unregistering or deleting a disk.

The OS task runs `scripts/storage_retention.py` daily. Validation tri-stems idle for 72 hours retire only after the existing dependency classifier permits them; tracked files, input references, unknown references, running consumers and active reservations stay. JSON and deletion hashes survive. Seven-day-idle validation directories use a 20 MB demotion floor, so 20–200 MB frozen/controlled Evidence no longer stays on SSD solely because it misses the general 200 MB floor; archival preserves their full bytes. Reference discovery skips relocated/broken junctions and package environments rather than traversing HDD archives or stopping on missing paths. The legacy Product payload archive (pre-`run.json` BGM runs under the Product state) is an HDD move, so it does not run while `move_to_hdd` is false.
